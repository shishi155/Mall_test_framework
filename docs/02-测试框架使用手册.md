# 02 · 测试框架使用手册（pytest + Allure）

> 框架形态：**接口为主、UI 冒烟为辅**，Excel 做用例设计与追溯，pytest 做执行，Allure 做报告
> 当前状态：✅ 163 条用例（138 接口/安全 + 11 UI + 14 Excel 驱动），141 通过 / 21 已知缺陷 xfail / 1 skipped

---

## 1. 分层结构

```
tests/              用例层：只写业务动作与断言，不拼 URL、不写 request
   ↑
api/                接口对象层：一个接口一个方法；registry.py 供 Excel 驱动调用
   ↑
common/             公共层：HTTP 客户端 / 断言 / 数据库 / 数据工厂 / Excel 读取
   ↑
config/             配置层：多环境 yaml + 环境变量覆盖
```

| 目录 | 职责 | 关键文件 |
|---|---|---|
| `config/` | 环境配置（地址/超时/DB/账号），支持环境变量覆盖 | `config.yaml`、`settings.py` |
| `common/` | 请求封装、断言、DB、数据工厂、Excel 读取、下单链路辅助、日志 | `http_client.py`、`assertions.py`、`db.py`、`data_factory.py`、`excel_loader.py`、`order_flow.py` |
| `api/` | 后台/前台接口对象 + Excel 接口注册表 | `admin/auth_api.py`、`admin/admin_api.py`、`portal/sso_api.py`、`portal/member_api.py`、`registry.py` |
| `tests/` | 用例，按端与模块分目录 | `admin/`（5 个模块）、`portal/`（8 个模块）、`security/`、`excel/` |
| `testcases/` | 用例 Excel、用例收集与生成脚本 | `mall_测试用例_v1.0.xlsx`、`collect_cases.py`、`build_case_workbook.py` |
| `reports/` | allure-results、allure-report、run.log | — |

```yaml

default_env: local

  local:
    admin:  { base_url: http://localhost:18080, timeout: 10 }
    portal: { base_url: http://localhost:8085,  timeout: 10 }
```

切换环境：

```powershell
python -m pytest --env=ci
```

| 变量 | 说明 |
|---|---|
| `MALL_ENV` | local / ci |

> 密码等敏感信息只存在于本地 yaml 与 CI 凭据中，不落用例代码。

## 3. 夹具（fixtures）清单

| 夹具 | 作用域 | 说明 |
|---|---|---|
| `settings` | session | 配置对象 |
| `admin_anon` | session | 未登录后台客户端 |
| `admin_token` / `admin_client` | session | 登录一次，全局复用 token |
| `admin_auth_api` / `admin_product_api` / `admin_order_api` | session | 后台接口对象 |
| `portal_sso_api` / `portal_anon` | session | 前台登录注册接口 |
| `portal_member` | session | **运行时注册的唯一会员**（手机号时间戳生成），含 token |
| `portal_client` | session | 已登录前台客户端 |
| `portal_cart_api` / `portal_order_api` / `portal_product_api` / `portal_home_api` | session | 前台接口对象 |
| `db` | session | MySQL 连接（DictCursor，autocommit） |
| `sellable` | session | **从库里挑一个「已上架 + 有库存」的商品与 SKU**，不写死 id |
| `clean_cart` | function | 用例前后清空购物车，避免脏数据干扰断言 |
| `ctx_factory` | session | 给 Excel 驱动用例构造「带/不带 token」的上下文 |

**为什么会员要运行时注册**：mall 的注册需要手机号验证码，固定账号在重复执行时会撞「已注册」；
时间戳生成手机号可无限次重复执行，且不污染业务数据（后续可加清理夹具）。

## 4. 断言库（`common/assertions.py`）

| 方法 | 用途 | 失败时输出 |
|---|---|---|
| `assert_success(resp)` | 业务成功 `code=200` | method/url/http/code/message/body 片段 |
| `assert_code(resp, 500)` | 指定业务码，可带 `msg_contains` | 同上 |
| `assert_failed(resp, (401,404,500))` | 业务失败，且不为 200 | 同上 |
| `assert_data_not_empty(resp, "list")` | data（或嵌套路径）非空 | 同上 |
| `assert_no_sensitive_leak(resp)` | 响应不回显 password/token 等 | 命中关键字 |
| `assert_fields(obj, {...})` | 批量字段校验 | 缺哪个字段 |
| `assert_db_equal(actual, expected)` | 接口值与库值比对 | 两侧值 |

> **关键约定**：mall 的接口 HTTP 状态码基本恒为 200，业务结果看 `body.code`。
> 断言一律走 `resp.code`，不看 HTTP 状态（`/product/detail/{不存在id}` 这类例外已单列缺陷 D-02）。

## 5. 新增一个接口（3 步）

```python
# 1) api/portal/sso_api.py 里加方法
def get_product(self, product_id: int) -> ApiResponse:
    return self.c.get(f"/cart/getProduct/{product_id}")

# 2) 需要被 Excel 驱动时，再注册一行（api/registry.py）
@register("portal.cart.getProduct")
def _(ctx, p):
    return ctx.anonymous_portal.get(f"/cart/getProduct/{p['productId']}")

# 3) 用例里直接用夹具调用
def test_xxx(portal_cart_api):
    resp = portal_cart_api.get_product(27)
```

## 6. 新增一条用例（两种粒度）

### 6.1 链路/业务用例（代码写流程）

```python
@allure.feature("前台-购物车")
@pytest.mark.smoke
@pytest.mark.case_id("MALL-POR-CART-001")   # 与 Excel 编号对齐
def test_cart_add_and_list(portal_cart_api, clean_cart, sellable):
    resp = portal_cart_api.add(sellable["product_id"], sellable["sku_id"], 1)
    A.assert_success(resp)
    items = portal_cart_api.list().data
    assert any(i["productSkuId"] == sellable["sku_id"] for i in items)
```

### 6.2 单接口校验点（Excel 驱动，不改代码）

在 `testcases/mall_测试用例_v0.2.xlsx` → 「参数化数据」页加一行：

| 用例编号 | 接口标识 | 方法 | 路径 | 传参方式 | 参数(JSON) | 携带token | 期望code | 期望message包含 | 期望data非空 | 备注 |
|---|---|---|---|---|---|---|---|---|---|---|
| MALL-ADM-SSO-002 | admin.login | POST | /admin/login | JSON | `{"username":"admin","password":"Wrong@123456"}` | 否 | 500 | 密码不正确 | 否 | 密码错误 |

执行时自动变成一条用例 `test_point_case[MALL-ADM-SSO-002]`，并在 Allure 里按编号打标签。

> 适用边界：**只处理「一次调用 → 校验 code/message/data」的简单场景**。
> 需要多步链路、动态取值、DB 断言的，仍用 6.1 写代码——这是 C 混合模式的分工。

## 8. 标记（markers）

| 标记 | 含义 | 用途 |
|---|---|---|
| `smoke` | 冒烟，主干链路 | 每次提交跑 |
| `regression` | 回归 | 每日/版本回归 |
| `security` | 安全专项 | 阶段六扩展 |

## 9. 已知缺陷的处理方式

用 `xfail` 表达「这条用例断言的是正确行为，但当前系统不满足」，而不是把错误行为写成期望：

```python
@pytest.mark.xfail(reason="已知缺陷 D-01：验证码明文返回", strict=False)
def test_auth_code_not_returned_plaintext(portal_sso_api): ...
```

好处：缺陷修复后用例自动转 PASS（XPASS 会提示），不会一直「假绿」；
报告里 xfail 数量就是**未修复缺陷数**，给管理层的信号很直接。

当前 3 条 xfail 对应缺陷 D-01 / D-02 / D-05。

## 10. 踩坑记录

| 现象 | 原因 | 处理 |
|---|---|---|
| 加购用例报「无可售 SKU」 | `mall.sql` 里 id=1 的商品 `delete_status=1` 且无 SKU 行 | 改用 `sellable` 夹具：从库中查 `delete_status=0 且 stock>0` 的商品 |
| 后台商品列表 total 与 `count(*)` 不符 | 接口过滤了 `delete_status=1` | 断言改为 `count where delete_status=0` |
| 购物车列表拿不到 price/productName | `/cart/list` 返回原始 `oms_cart_item`，价格在 `/cart/getProduct/{id}`，促销在 `/cart/list/promotion` | 三个接口配合断言 |
| 密码错误返回 500 而不是 404 | mall 的 `UmsAdminServiceImpl` 对「账号不存在」与「密码错误」返回不同码 | 属缺陷 D-05，用例拆成「行为记录」+「防枚举 xfail」 |
| 控制台中文乱码 | Windows 控制台 GBK | 会话内 `[Console]::OutputEncoding=[Text.Encoding]::UTF8`；文档/日志统一 UTF-8 |
| `pytest` 报 `ModuleNotFoundError: config` | 未在项目根目录执行 | `pytest.ini` 已配 `pythonpath = .`，务必在工程根目录跑 |

## 12. 用例台账自动生成（避免 Excel 与代码两张皮）

用例详情页不是手写的，而是**从 pytest 源码收集**出来的：

```powershell
.\.venv\Scripts\python.exe testcases\collect_cases.py   # 扫描 tests/ → build/cases.json
.\.venv\Scripts\python.exe testcases\build_case_workbook.py  # 生成 Excel V1.0
```

收集内容（以代码为唯一事实来源）：

| 字段 | 来源 |
|---|---|
| 用例编号 | `@pytest.mark.case_id("MALL-XXX")` |
| 用例标题 / 子模块 | `@allure.title` / `@allure.story` |
| 所属端 / 模块 | 测试文件所在目录与文件名 |
| 用例类型 / 优先级 | 标记（smoke/security/point）+ 标题关键词 + 所属模块 |
| 关联接口 | 函数体里第一个 `/` 开头的路径字面量 |
| 自动化用例 ID | `文件::函数名`（可直接 pytest 指定执行） |
| 缺陷关联 | `@pytest.mark.xfail(reason="已知缺陷 D-xx：...")` |
| 前置条件 / 测试数据 / 步骤 / 预期 | 模块默认模板 + `collect_cases.py` 中 `OVERRIDES` 精修（P0 与缺陷用例必须人工精修） |

**约定**：新增用例后必须重跑这两个脚本，Excel 才会同步；CI 里可在构建阶段校验
「用例数 == pytest 收集数」，防止有人只改代码不改台账。

## 13. UI 自动化（Selenium，阶段四）

### 13.1 结构

```
ui/
├─ browser.py     # 驱动创建 + 失败证据采集（截图 / DOM / 控制台日志）
└─ pages.py       # Page Object：LoginPage / LayoutPage / ProductListPage / OrderListPage
tests/ui/
├─ conftest.py    # driver 夹具（每用例独立 profile）+ 失败自动取证 hook
└─ test_ui_smoke.py
```

### 13.2 本机三个坑（已在代码里规避）

| 现象 | 原因 | 解法 |
|---|---|---|
| `session not created: cannot create temp dir` | Chrome 继承了受限的 TEMP | 把 `TEMP/TMP` 指到 `build/tmp` 再启动 |
| chromedriver 版本不匹配（156 vs 151/152） | Selenium Manager 拉的驱动与 Chrome 大版本不一致 | 从 npmmirror 下载对应版本，`Service(executable_path=...)` 显式指定 |
| 登录后 `/#/login` 直接跳首页 | 上一个用例残留的 localStorage token | 每个 driver 用独立临时 profile，退出时删除 |

### 13.3 登录页的特殊处理

登录页会把用户名预填成 `admin`，用 `send_keys` 会变成 `adminadmin`（且 `.clear()` 不触发 Vue 的 v-model 更新）。
统一用 JS 赋值并派发 `input` 事件：

```python
SET_VALUE_JS = """
const el = arguments[0], val = arguments[1];
el.value = val;
el.dispatchEvent(new Event('input', {bubbles: true}));
"""
```

### 13.4 失败取证

`tests/ui/conftest.py` 的 `pytest_runtest_makereport` 在用例失败（含 setup 失败）时调用
`capture_evidence(driver, case_name)`：

- `reports/ui-evidence/<用例名>_<时间戳>/screenshot.png` —— 全屏截图
- `page.html` —— 失败瞬间的 DOM 快照
- `console.log` —— 浏览器控制台日志（含 `SEVERE` 错误）
- `context.json` —— URL / 标题 / 窗口尺寸
- 以上四项同时 attach 到 Allure，报告里可直接查看
